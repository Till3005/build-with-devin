# ガイド 9 — プレイブックとナレッジ：組織の規約をエンコードする

**目標：** 最高のエンジニアが当たり前と思っていることを書き下し——プレイブック（再現可能な手順）とナレッジ（恒常コンテキスト）として——Devin セッションと Bot を組織スケールで信頼できるものにする。
**レベル：** 中級 · 大規模な公開導入すべてに共通する層
**出典：** [docs.devin.ai](https://docs.devin.ai) · [ガイド 7](enterprise-playbook.md) の導入教訓

## なぜこの層がすべてを決めるのか

公開されたすべてのエンタープライズ成果——Nubank の 8–12 倍、EBANX の 92% 自作成 PR、Wayfair の 1,600 席——はエンコードされた規約の上に立っている。それがなければ、Devin の出力はセッションごとにばらつく：毎回あなたのスタック、マージルール、テスト習慣を再発見する。あれば、500 回目のセッションも、最高の調子の日の最高のエンジニアのように振る舞う。

相補的な 2 つの成果物：

| 成果物 | 内容 | たとえ |
| --- | --- | --- |
| ナレッジ | Devin が読む恒常コンテキスト——リポジトリの事実、規約、環境の落とし穴 | オンボーディング資料 |
| プレイブック | 名前付きの再現可能な手順——トリガー、手順、受入基準 | 誰でも呼べるランブック |

## ステップ 1 — 自分の修正を掘り起こす

最も安いナレッジはすでに存在する：過去 20 の Devin セッションを遡り、あなたが修正を打った箇所をすべて集める——*「デプロイは Cloud Run」*、*「`git push --force` は絶対禁止」*、*「テスト前に `npm run db:seed` が要る」*。各修正は、重要だった証拠つきのナレッジ項目である。

掘り起こす対象は他にも：
- 人間が Devin の PR に繰り返し書くコードレビューコメント
- 変更が*なぜ*その形になったかを説明する PR 説明文
- オンボーディング資料——新入社員に伝えること全般

## ステップ 2 — 残るナレッジ項目を書く

良い項目は 1 行、命令形、スコープ付き：

```text
- Deploy only via `make deploy-cloudrun` — never run gcloud directly.
- Migrations require a matching rollback file in prisma/rollbacks/.
- The staging seed user is qa+admin@corp.io; never create real-looking users.
```

悪い項目は小説、願望（「いいテストを書け」）、またはシークレット（クレデンシャルをナレッジに入れるな——シークレットストアを使え）。

## ステップ 3 — 再現可能な作業のプレイブック化

> **プラットフォーム更新（2026年11月）：** Playbook は **Skills** へ移行中 — アカウントは順次移行され、新規アカウントは Skills のみ（各 playbook は同じ org/enterprise スコープの skill になります）。本ステップの内容はすべて skills にそのまま適用できます：skill は同じ、呼び出し可能な名前付き手順です。


プレイブックは手順をパッケージ化し、どのセッション（や Bot）も同じやり方で実行できるようにする。機能する構造：

```markdown
# <動詞 + 目的語> — 例："Cut a release"
## When to use
<トリガー条件>
## Steps
1. <決定的な手順>
2. ...
## Acceptance
<合否チェック>
## Failure modes
- <既知の破損 → 対処>
```

組織全体に公開し、セッション・自動化・Bot のすべてが呼べるようにする——これが一回きりの成功セッションを組織能力に変える。

## ステップ 4 — Bot への供給

Bot の **Instructions**（ガイド 1）はナレッジの Bot スコープ版——全セッション開始時に読まれるルール。職務の法律はそこへ、組織の法律はナレッジへ、手順はプレイブックへ。層分けが各成果物を小さく最新に保つ。

## ステップ 5 — 修正ループ

ナレッジは腐る。真実を保つループ：

1. セッション/Bot が間違える → チャットで修正
2. Bot が修正をメモリに書く（またはナレッジに追加）
3. 週次レビュー：繰り返し現れる Bot メモリ項目を組織ナレッジに昇格；1 か月誰も発動していない項目は削除

まさにこのための公式 Bot テンプレート Devin Coach がある——Devin がどこで詰まったかを週次報告し、毎回 1 つの修正案（メモ、スキル、セットアップ変更）を提示する。

## 検証チェックリスト

- [ ] あなたのリポジトリでの新規セッションが、ナレッジに答えのある質問をゼロ件尋ねる
- [ ] Bot に与えた直近の修正がそのメモリファイルに現れている
- [ ] 異なる 2 つのセッションが同じプレイブックを実行し、同じ形の結果を出す

## 落とし穴

- **願望を書く。** 「ベストプラクティスに従え」は何も変えない；「テスト前に `npm run db:seed` を実行せよ」はすべてを変える。
- **放置。** 陳腐化したナレッジは無いより悪い——Devin は自信満々に従う。月次でレビュー。
- **ドキュメントの複製。** ナレッジに入れるべきは Devin が*間違える*か*知り得ない*ものであり、wiki のコピーではない。

## 理解度チェック

1. プレイブックとナレッジの違いは？*（プレイブックは名前付きタスクの再現可能な手順；ナレッジは全セッションが前提とすべき恒常コンテキスト）*
2. 「最高のエンジニアが当たり前と思うことを書き下せ」が実際のエンタープライズ・ボトルネックなのはなぜ？*（エージェントの品質は限界ではなかった——欠けたコンテキストが限界；ナレッジ層は組織の規約が住む場所）*
3. 規約が部族知識のままではなくプレイブックになるのはいつか？*（セッションが、書かれた手順が防げたはずの形で間違えた最初の瞬間）*
