# ガイド 13 — 公式ユースケース・クックブック

**目標:** Cognition 公式ドキュメントで実証済みの使用パターンをクックブックとして整理 — Devin に切り分けるべき仕事とは何か、そしてプロンプト付きでコピーできる 40 以上の文書化レシピ。
**レベル:** まずは網羅性のためにここから
**出典:** [Best Practices](https://docs.devin.ai/use-cases/best-practices.md) · [Use-case gallery](https://docs.devin.ai/use-cases/gallery/index.md) · [use-case tutorials](https://docs.devin.ai/use-cases/index.md)

## すべてを貫く唯一のルール

公式ガイダンスのロジックをそのまま言うと:**wide & shallow**(広く浅い)仕事を選べ — シンプルで水平方向にスケールするタスクの大きなバックログは、複雑な新規構築に常に勝る。

| 理想的なタスク | アンチタスク |
| --- | --- |
| ジュニアエンジニア程度の複雑さの反復的サブタスク | 新規の複雑な機能 |
| スライスあたり手作業 90 分未満 | 分割不可能なもの |
| 客観的な合否検証 | 「なんか良さそう」 |
| 分離され、後方互換で、並列化可能 | 絡み合った依存関係 |

ドキュメントにある 4 つの優れたスライス形:**マイグレーション、リファクタ、モダナイゼーション、技術的負債バックログ。**

## レシピカタログ

以下はすべて公式ギャラリーに文書化されたユースケース — それぞれコピペ可能なプロンプト付き。人間の週から取り除いてくれる仕事別に整理。

### インシデント & 本番健全性

| レシピ | 仕組み |
| --- | --- |
| Datadog/PagerDuty アラートの自動調査 | Webhook/API トリガー → 発火時にセッションが調査 |
| ポストモーテムの自動生成 | PagerDuty 解決 → Devin がタイムライン・根本原因・アクションアイテムを起草 |
| Sentry エラーの毎日修正 | 夜間 cron が新規エラーを取得 → 朝には修正 PR |
| バグレポートの end-to-end デバッグ | レポート + Datadog ログ + DB アクセスを Devin に渡す → 根本原因 |

### 定期ハイジーン(ドキュメントで最も ROI の高いページ)

| レシピ | 頻度 |
| --- | --- |
| 週次の依存関係更新 PR | 週次:古いパッケージ → テスト済みアップグレード PR |
| ステージングでの夜間 E2E | 夜間:スイート実行、失敗分をチケット化 |
| マージ済み PR からの週次変更履歴 | 金曜:分類済み変更履歴 → Slack |
| Datadog ヘルスの日次ダイジェスト | 日次:エラースキャン → Slack ダイジェスト |
| デザインシステムの日次監査 | 日次:マージ済み PR のハードコード色・欠落トークンを検出 |
| フィーチャーフラグの掃除 | リリース後に一度だけのセッションでフラグ + デッドコードを剥がす |
| Notion ステータスの週次ダイジェスト | 週次:PR/コミット要約 → Notion |
| 会議議事録からの PR | 毎時:Granola をポーリング → エンジニアリングタスク抽出 → 子セッション |

### コード品質

| レシピ | 仕組み |
| --- | --- |

| ビジュアルリグレッションの捕捉 | リポジトリスキル:PR 前に影響ページすべてをスクリーンショット |
| 全 PR のマイグレーションチェックリスト | リポジトリスキルが破壊的操作を捕捉し、スキーマ変更を検証 |

## このクックブックの使い方

1. **定期ハイジーン**から 1 レシピ選ぶ — 最も安い初勝利(考えなくても回り続ける夜間/週次ループ)
2. PagerDuty/Datadog/Sentry があれば **インシデント**から 1 つ追加
3. レシピが動いたら **スキル**(ガイド 12)か **Bot**(ガイド 1–5)に凍結する — 上の行すべてはどちらかの形で生き残る

## 検証チェックリスト

- [ ] ハイジーンレシピ 1 つがスケジュールで動き、最初の PR/レポートを出した
- [ ] その出力がスキル・プレイブック・Bot に凍結されている — 誰かの頭の中に住んでいない

## 落とし穴

- **レシピ 10 個、凍結ゼロ。** 手動プロンプトのままのレシピは金曜には忘れられる — 運用化するか捨てるか。
- **自社リポジトリの検証なしのコピペプロンプト。** ギャラリーのプロンプトはテストスイートの存在を前提にしている;タスクだけでなく*チェック*を適応させる。

## 理解度チェック

1. なぜインシデント対応より先に定期ハイジーンレシピから始めるのか?*(最も安い勝利だから — 寝ている間に回り、夜間 lint 修正の失敗は回復可能だが、インシデント操作の失敗は回復不能だ。)*
2. 「レシピをスキルか Bot に凍結する」とは実際に何を防ぐのか?*(プロンプトドリフトと個人依存 — レシピは書いた人を越えて生き残る。)*
3. なぜタスク部分より先にギャラリープロンプトの検証部分を適応させるのか?*(タスクは意図を記述するだけ;チェックこそが自社リポジトリが実際に証明できるもの — 間違ったチェックは自信満々のゴミを生む。)*
