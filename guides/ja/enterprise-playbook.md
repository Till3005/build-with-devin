# ガイド 7 — エンタープライズ導入パターン

**目標：** 公開済みの数値を実際に生んだ形を使って Devin を組織スケールで導入する——実験ではなく、実証済みの動作。
**レベル：** 中級（エンジニアリングリード向け）
**出典：** 公開された顧客事例、[devin.ai/customers](https://devin.ai/customers)

結果を公開した企業から抽出した 6 つの導入形。成功した導入のほとんどは 6 つ全部ではなく 2〜3 を使っている。

## 形 1 — レガシー移行エンジン（Nubank、Comarch）

| | |
| --- | --- |
| 導入 | Nubank：数百万行・8 年物の ETL モノリス → サブモジュールへ。Comarch：20 年・1,000 万行の ERP 再構築。Odyssey Logistics（Cognizant）：Access/VBA TMS → クラウドネイティブ、**ネットコスト 37% 削減** |
| 結果 | エンジニアリング効率 8–12 倍、コスト 20 分の 1（Nubank） |
| 機構 | *自社*コードベースで Devin をファインチューン（Nubank は 1 タスク約40分→約10分）、その後リライトではなく追跡される小さな PR 群として移行プログラムを継続実行 |

**真似る方法：** 境界のあるレガシーシステムを 1 つ選ぶ；ファインチューンまたはプレイブックで教育；Migration Engineer 型ループを回す——大きな移行を、進捗の見える小さな追跡 PR 群として。勝利は複利で効く：移行済みモジュール一つごとが次のセッションを賢くする。

## 形 2 — 第一作者リポジトリ（EBANX、Gumroad、Finch）

| | |
| --- | --- |
| 導入 | EBANX：**マージ PR の 92% が Devin 作成**。Gumroad：Devin はリポジトリの**第 1 コントリビューター**（1,500+ PR）。Finch：3,000 PR、エンジニア約 20 人月を節約。Gamma：約 10 エージェントのフリート + エンジニア 3 名が PowerPoint インポートを再構築——**3,500+ マージ**、5–10 エンジニア×1 年と見積もられた作業 |
| 機構 | これらのリポジトリで Devin はアシスタントではない——デフォルトの作者。人間はレビューと方向付け |

**真似る方法：** 高速なリポジトリを 1 つ選ぶ；チケットをデフォルトで Devin セッションに回す；人間はレビュー。見るべき指標は自作成 PR 比率——約 50% 超ならこの形；未満ならまだパイロット段階。

## 形 3 — 常駐ファーストレスポンダー（Modal、Reducto、AngelList）

| | |
| --- | --- |
| 導入 | Modal：**インシデントの 80% が、エンジニアがスレッドを開く前に調査済み**。Reducto：Devin Oncall が第一応答者；エンジニアがページされることは稀。AngelList：Devin がインシデントの 70% をエンジニアより先に原因究明 |
| 機構 | PagerDuty/Slack トリガー → ログ/リポジトリアクセス付きセッションが調査 → 人間が起きる前にレポート到着 |

**真似る方法：** [Devin Oncall](https://docs.devin.ai) か PagerDuty トリガーの自動化（ガイド 6、レシピ：インシデント → 調査）。事前調査済みインシデントの % を測る——1 ポイントごとが人間の回復された睡眠。

## 形 4 — メンテナンス艦隊（Airbyte、Melius）

| | |
| --- | --- |
| 導入 | Airbyte：**700+ コネクタ**を稼働維持。Melius：1 日約 100 PR |
| 機構 | 誰もやりたがらないロングテール——コネクタの腐敗、依存関係の漂流、古いフラグ——を継続的に消化する Bot/自動化に流す |

**真似る方法：** メンテナンスバックログ（エンジニアが避ける作業）を列挙；Code Health Engineer / Code Reaper 型 Bot（公式テンプレート）で包み、週次ケイデンスを設定。

## 形 5 — 組織全体のシート（Wayfair、The Access Group、Citi）

| | |
| --- | --- |
| 導入 | Wayfair：1,600+ エンジニアが全員利用。Access Group：250 プロダクト・2,000+ エンジニアに Devin → 出力 5 倍。Citi：40,000 開発者への展開、技術ベンダー支出 30% 削減 |
| 機構 | エージェントを増やすのではなく*シート*：全エンジニアが Devin アクセス、共有プレイブック、組織レベルのナレッジを持つ |

**真似る方法：** 公開事例での展開順は一貫している——パイロットチーム → 計測された結果 → プレイブック/ナレッジの標準化 → シート拡大。ナレッジのステップを飛ばすのがシート展開が停滞する理由：[プレイブックガイド](playbooks-and-knowledge.md)参照。

## 形 6 — プロセスゲート（Hamming、Litera、Eight Sleep）

| | |
| --- | --- |
| 導入 | Hamming：Devin がコード量の 25% を記述。Litera：回帰サイクル 90% 短縮。Eight Sleep：出荷量 8 倍。Zeb：NetSuite→Databricks デリバリー **4 週間 → 2.5 週間**、別件の未公開 Fortune 500 エネルギー企業：**8 日で 142 オブジェクト** |
| 機構 | Devin はパイプラインの一段階——回帰テスト、QA——を所有する。製品全体ではない |

**真似る方法：** 人間コストが最悪のパイプライン段階（回帰サイクル、QA）を見つける；Bot か自動化に割り当てる；その段階のサイクルタイムを前後で測る。

## 事例が示唆するアンチパターン

- **同僚ではなくツール。** 高い数値の導入は Devin にタスクではなく所有（リポジトリ、サーフェス、段階）を与えている——ガイド 1–5 と同じ教訓。
- **永遠のパイロット。** 公開された結果の共通点：*卒業した*計測付きパイロット。卒業基準（PR 比率、カバーしたインシデント、節約時間）を事前に決める。
- **ナレッジ層なし。** すべての大規模導入がどこかに規約をエンコードしている——ファインチューン、プレイブック、Bot instructions。それがなければ品質はセッションごとにばらつく。

## 落とし穴

- **卒業しなかったパイロットのスケーリング。** ここにある大きな数値はすべて、出口基準のある計測付きパイロットの後に来た。
- **ライセンス先行の思考。** 所有する段階を指名する前にシートを買うと棚に飾られる——パターンは段階 → パイロット → 指標 → それからシート。

## 理解度チェック

1. なぜ 6 つの導入形すべてが「所有する段階」を原子にしているのか？*（公開された数値はすべて境界のある計測可能な領域から来た——「至る所」に導入した組織は何も公開していない）*
2. 卒業基準とは何か、なぜパイロット前に決めるのか？*（パイロット→本番を切り替える指標 + 閾値；それがなければパイロットは永遠に漂流するか雰囲気で殺される）*
3. なぜすべての大規模導入にナレッジ層が現れるのか？*（スケールでの一貫性には共有コンテキストが必要——代替案は品質の異なる N 個のセッション）*
